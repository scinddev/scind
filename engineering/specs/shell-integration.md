# Scind Shell Integration Specification

**Version**: 0.2.0-draft
**Date**: August 2026
**Status**: Design Phase

This document defines Scind's shell integration, including standard CLI completion and Docker Compose passthrough with delegated completion.

---

## Overview

Scind provides two complementary interfaces:

1. **`scind` CLI**: The primary command for managing workspaces, applications, ports, and configuration. Uses standard completion generated by Cobra.

2. **`scind-compose` binary**: A context-aware passthrough to `docker compose` that automatically injects the correct project name and compose files based on the current directory or explicit flags. It is a **real executable shipped next to `scind`**, not a shell function. Its completion delegates to Docker's own completion.

This separation exists because:

- Docker Compose has ~20 subcommands with hundreds of flags and options
- Reimplementing completion for all of them would be significant work with no added value
- Users already know `docker compose` — we just make it workspace-aware
- Completion delegation achieves full docker compose completion "for free"

### Why a binary and not a shell function

Earlier drafts of this spec made `scind-compose` a **sourced shell function** that called `scind compose-prefix` and `eval`ed its output. The stated reason was completion economics: the belief that only a shell function can hand its completion context to Docker's completion machinery.

That belief is disproven. The Xcind proof-of-concept ships `bin/xcind-compose` as a standalone executable and still gets genuine delegated completion, because the completion script delegates by **calling the `docker` binary's Cobra completion protocol** (`docker __complete compose …`) rather than by re-entering a sourced `_docker` function. Xcind's `test/test-xcind-completion.sh` (137 assertions, run on the Bash 3.2 matrix) drives the completion functions the way an interactive shell does and proves the delegated path offers:

- `docker compose` subcommands that no hardcoded list carries (`ls`, `watch`, `cp`);
- per-subcommand flags (`up --detach`, `up --build`, `logs --follow`);
- **service names read from the resolved compose file** — the decisive case, because a static list can never produce them.

A binary is the simpler design once that constraint is gone. It removes the sourced function, the `eval` indirection, and the empty-output error-detection workaround the eval contract needed. The one cost carried over from Xcind: delegation needs a `docker` CLI that supports Cobra's `__complete`, so the completion script keeps a **hardcoded subcommand fallback** for hosts where it is missing. The trade is eval indirection for a fallback list, not for nothing.

This change comes from the Xcind proof-of-concept (Xcind ledger row `RL-112`).

## CLI Completion

Scind provides shell completion for all commands.

### Installation

**Bash**:
```bash
source <(scind completion bash)
# Or add to ~/.bashrc:
# echo 'source <(scind completion bash)' >> ~/.bashrc
```

**Zsh**:
```bash
source <(scind completion zsh)
# Or add to ~/.zshrc
```

**Fish**:
```bash
scind completion fish | source
# Or save to completions directory
```

### Features

Completion supports:
- Command and subcommand names
- Flag names and values
- Workspace names (from registry)
- Application names (from current workspace)

## Architecture

```
┌─────────────────────────────────────────────────────────────────────┐
│                         User's Shell                                │
│                                                                     │
│   scind workspace up          scind-compose exec php bash           │
│         │                                    │                      │
│         ▼                                    ▼                      │
│   ┌───────────┐                    ┌─────────────────┐              │
│   │ scind     │                    │ scind-compose   │              │
│   │  binary   │                    │    binary       │              │
│   └───────────┘                    └────────┬────────┘              │
│         │                                   │                       │
│         │                          resolves context                 │
│         │                          in-process (same                 │
│         │                          resolver as scind)               │
│         │                                   │                       │
│         │                                   ▼                       │
│         │                    ┌──────────────────────────┐           │
│         │                    │  exec docker compose     │           │
│         │                    │  -p dev-frontend         │           │
│         │                    │  -f docker-compose.yaml  │           │
│         │                    │  -f override.yaml        │           │
│         │                    │  exec php bash           │           │
│         │                    └──────────────────────────┘           │
│         │                                                           │
│   Completion:                Completion:                            │
│   Standard CLI framework     Completion script calls                │
│   (Cobra, Click, etc.)       `docker __complete compose …`          │
│                              (hardcoded fallback if absent)         │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

There is no `eval`, no sourced function, and no prefix string on the invocation path. `scind-compose` resolves workspace, application, flavor, and compose files itself, then `exec`s `docker compose`.

## The `scind-compose` Binary

### Behavior

`scind-compose` accepts Scind targeting flags first, then passes every remaining argument through to `docker compose`:

```bash
$ cd ~/workspaces/dev/frontend
$ scind-compose exec php bash
# → exec docker compose -p dev-frontend \
#     -f '…/frontend/docker-compose.yaml' \
#     -f '…/dev/.generated/frontend.override.yaml' exec php bash
```

### Flags

| Flag | Short | Description |
|------|-------|-------------|
| `--workspace` | `-w` | Specify workspace (overrides context detection) |
| `--app` | `-a` | Specify application (overrides context detection) |

Argument parsing stops consuming Scind flags at the first positional argument or unrecognized flag; everything from that point on belongs to `docker compose`.

> **Note**: There is no `--flavor` flag. Flavor changes require regeneration and can impact running applications, so flavor must be set explicitly via `scind flavor set` before using `scind-compose`.

### Error Behavior

If context cannot be resolved, `scind-compose` prints the error to stderr and exits with code 5 — directly, on its own. It does **not** call a helper command, inspect empty output, or re-run anything to obtain the message:

```bash
$ cd ~
$ scind-compose ps
Error: No application context detected.

Either:
  1. Run from within an application directory
  2. Specify explicitly: scind-compose -a APP [command]

Available workspaces: scind workspace list
$ echo $?
5
```

When context resolves, `scind-compose` `exec`s `docker compose` and therefore **returns Docker Compose's own exit code** unchanged.

### Exit Codes

| Code | Meaning |
|------|---------|
| 5 | Context detection failed (no workspace/app found) |
| 1 | General error (configuration issues, file not found, etc.) |
| _other_ | Passed through from `docker compose` |

## Completion Delegation

`scind-compose`'s completion script builds the completion request the user *would* have typed against Docker and asks the `docker` binary directly, using Cobra's completion protocol:

1. Rewrite the current words as `docker __complete compose <words…>`, appending an empty argument when the cursor sits after a space.
2. Run that command and read its output: one completion per line (value, optional TAB, description), with a final `:N` directive line.
3. On directive bit 1 (error) or empty output, fall back (below). Otherwise offer the values, honoring directive bit 2 (no trailing space).

Because step 1 executes the real `docker` binary, flags come from the installed Compose version and **service names come from a real compose file**, not a hand-maintained list. This is the property that a static list can never reproduce, and it is what Xcind's tests pin.

The `-w`/`-a` words are dropped from the delegated request — they are Scind's, not Docker's — and their values are completed from `scind workspace list -q` / `scind app list -q` instead.

**Scope of the delegated context.** The request carries no `-p`/`-f` flags, so `docker compose` discovers compose files exactly as it would if the user ran it directly: from the current directory. Service-name completion is therefore correct in the common case (completing inside the application directory) and falls back to Docker's own discovery elsewhere — completing `scind-compose -a backend exec <TAB>` from the workspace root offers whatever Docker finds there, not `backend`'s services, and services that exist only in the generated override are not offered. See [Known Limitations](#all-shells).

### Hardcoded Fallback

Some hosts ship a `docker` CLI without Cobra's hidden `__complete` command. The completion script then offers a **static list of `docker compose` subcommands** only, and offers nothing for arguments it cannot know (service names, per-subcommand flags). The fallback must never invent commands the local Docker does not have; it is a degraded path, not a second source of truth.

## The `scind compose-prefix` Command

`compose-prefix` outputs a docker compose command prefix for the resolved context. It is **no longer load-bearing**: nothing in Scind's shell integration consumes it, and it is not required for `scind-compose` or for completion.

It is retained as a convenience for **scripting consumers** that want the resolved `-p`/`-f` text to embed in their own command lines. Consumers that want to *run* something should call `scind-compose`; consumers that exec a PATH binary should use [generated wrappers](#docker-wrapper-scripts).

### Behavior

```bash
$ cd ~/workspaces/dev/frontend
$ scind compose-prefix
docker compose -p dev-frontend -f '/home/user/workspaces/dev/frontend/docker-compose.yaml' -f '/home/user/workspaces/dev/.generated/frontend.override.yaml'

$ cd ~/workspaces/dev
$ scind compose-prefix -a backend
docker compose -p dev-backend -f '/home/user/workspaces/dev/backend/docker-compose.yaml' -f '/home/user/workspaces/dev/backend/docker-compose.worker.yaml' -f '/home/user/workspaces/dev/.generated/backend.override.yaml'
```

### Flags

| Flag | Short | Description |
|------|-------|-------------|
| `--workspace` | `-w` | Specify workspace (overrides context detection) |
| `--app` | `-a` | Specify application (overrides context detection) |

> **Note**: There is no `--flavor` flag. Flavor changes require regeneration and can impact running applications, so flavor must be set explicitly via `scind flavor set` before using `scind-compose`.

### Output Format

- All paths are single-quoted to handle spaces and special characters
- Compose files are included in the correct order (base files first, then generated override)
- Project name follows the `{workspace}-{app}` convention
- Output is a single line

### Error Behavior

If context cannot be resolved, the command exits with code 5 and prints an error to stderr:

```bash
$ cd ~
$ scind compose-prefix
Error: No application context detected.

Either:
  1. Run from within an application directory
  2. Specify explicitly: scind-compose -a APP [command]

Available workspaces: scind workspace list
$ echo $?
5
```

### Exit Codes

`scind compose-prefix` uses standard Scind exit codes:

| Code | Meaning |
|------|---------|
| 0 | Success - prefix output to stdout |
| 1 | General error (configuration issues, file not found, etc.) |
| 5 | Context detection failed (no workspace/app found) |

Scripts that call `compose-prefix` must branch on its **exit code**. The empty-output test that the old shell function used — running the command twice, once silenced and once to surface the error — is retired along with the function.

## Usage Examples

### Basic Usage

```bash
# From within an application directory (context detected)
$ cd ~/workspaces/dev/frontend
$ scind-compose exec php bash
$ scind-compose logs -f
$ scind-compose up -d

# From workspace root with explicit app
$ cd ~/workspaces/dev
$ scind-compose -a backend exec php bash
$ scind-compose -a frontend logs -f php

# From anywhere with explicit workspace and app
$ scind-compose -w dev -a frontend ps
```

### Tab Completion Examples

```bash
# Complete subcommands
$ scind-compose [TAB]
build   config  create  down    events  exec    images  kill    logs ...

# Complete service names (from the compose file Docker discovers here)
$ cd ~/workspaces/dev/frontend
$ scind-compose exec [TAB]
php     nginx   mysql   redis

# Complete docker compose flags
$ scind-compose exec -[TAB]
-d          --detach        -e          --env
--index     --no-tty        --privileged ...

# Complete with explicit app (scind flags first)
$ scind-compose -a [TAB]
frontend     backend     shared-db

# Explicit -a targeting completes the app name, but service names still come
# from Docker's discovery in the current directory — see Known Limitations
$ scind-compose -a backend exec [TAB]
php     nginx   postgres    worker
```

## Prompt Segment

Scind can render a context-aware prompt segment showing the current workspace/app and a clickable apex URL. It is surfaced by the `scind prompt` command (see the [CLI Reference](../reference/cli.md#scind-prompt)) and wired into a prompt framework via a generated snippet. This is a new capability contributed by the Xcind proof-of-concept—Scind previously had no prompt concept, only `scind-compose` and completion.

### What it shows

- The active **workspace** and **app** (from directory context)
- The application's **apex URL**, emitted as an **OSC 8 hyperlink** so supporting terminals render it clickable and others fall back to plain text

### Fast context-only detection path

Because a prompt segment runs on *every* command, it must be cheap. `scind prompt` (and its `--detect` probe) use a **context-only path** that:

- Resolves workspace/app/apex from directory context and persisted state (`.generated/`, the registry) only
- **Stops before any Docker or live-introspection work**—it never queries containers, contacts the proxy, or performs generation
- Targets a **sub-500 ms** budget so it is safe to invoke per-prompt

This mirrors the read-only, side-effect-free contract for introspection commands described in the [CLI Reference](../reference/cli.md#json-introspection-contract).

### Starship integration

```bash
scind prompt --generate starship
```

emits a ready-to-paste [`custom` module](https://starship.rs/config/#custom-commands) for `~/.config/starship.toml`:

```toml
[custom.scind]
command = "scind prompt --quiet"
when = "scind prompt --detect"
format = "[$output]($style) "
```

`when = "scind prompt --detect"` gates the segment on the cheap availability probe (exit 0 inside a Scind context, non-zero outside, no output), so it only appears where relevant. For hand-rolled prompt formats, `--print <field>` returns a single value (`workspace`, `app`, `apex`, or `url`).

## Docker Wrapper Scripts

`scind-compose` is a binary, so scripts and CI can call it directly. But some tools—**JetBrains IDEs, CI runners, and other harnesses**—do not call a Compose command of your choosing at all: they exec a literal `docker` or `docker-compose` found on PATH, with no setting that would point them at `scind-compose`. For those, `scind generate-wrappers` (see the [CLI Reference](../reference/cli.md#scind-generate-wrappers)) writes **real executable wrapper scripts**. This capability comes from the Xcind proof-of-concept.

### What is generated

- Two executable files, `docker` and `docker-compose`, written into a target directory (default `./.scind/bin`)
- Each embeds the **resolved project name and compose files** for the context—the same `-p`/`-f` set that `scind compose-prefix` produces
- Invoking a wrapper injects those flags and passes the remaining arguments through to the real Docker binary

### Using them

Put the wrapper directory on PATH (or point the tool's Docker executable setting at it):

```bash
scind generate-wrappers -a backend --dir .scind/bin
PATH=".scind/bin:$PATH" docker-compose ps   # workspace-aware
```

A JetBrains IDE, for example, can be configured to use `.scind/bin/docker-compose` as its Compose executable so its Docker integration operates on the correct project and files.

### Relationship to `scind-compose`

Wrapper scripts **complement**, and do not replace, `scind-compose`:

| | `scind-compose` binary | Generated wrapper scripts |
|--|------------------------|---------------------------|
| Consumer | Anything that can name the command — shells, scripts, CI | Tools hardwired to exec `docker`/`docker-compose` from PATH |
| Context | Resolved live per invocation | Baked in at generation time |
| Regeneration | Never needed | Re-run if the context or compose files change |

Prefer `scind-compose` everywhere you control the command name; reach for wrappers only when a tool cannot be pointed at it.

## Known Limitations

### All Shells

1. **`docker __complete` must exist**: Delegation calls the `docker` binary's Cobra completion protocol. On a `docker` CLI that lacks it, completion degrades to the hardcoded subcommand fallback — no service names, no per-subcommand flags.

2. **Per-completion latency**: Every delegated completion runs `docker __complete`, which resolves the compose files. This is a subprocess per TAB.

3. **Delegated completion is directory-scoped, not context-scoped**: The delegated request carries no `-p`/`-f`, so service names come from Docker's own compose-file discovery in the current directory. Completing for an explicitly targeted app (`-a backend`) from outside that app's directory, or for a service that exists only in the generated override, will not offer the right names. Invocation is unaffected — `scind-compose` always resolves the full context before exec'ing.

4. **Path spaces**: Paths with spaces are supported; `scind-compose` passes compose file paths to `docker compose` as separate arguments, so no quoting round-trip is involved.

### Bash-Specific

1. **Word splitting**: The completion script reconstructs the argument list from `COMP_WORDS`, which can lose original spacing inside quoted arguments.

### Zsh-Specific

1. **1-indexed arrays**: The completion function must account for zsh's 1-indexed arrays when calculating positions.

### Fish-Specific

1. **`complete -C` overhead**: Fish's completion delegation spawns a subshell, adding latency compared to bash/zsh.

2. **Completion caching**: Fish aggressively caches completions. If compose files change, completions may be stale until the shell restarts.

## Future Considerations

### Potential Enhancements

1. **Completion caching**: Cache the resolved context for a short duration to reduce latency on repeated completions.

2. **Context-scoped delegation**: Give `scind-compose` a hidden `__complete` passthrough that resolves the context, then runs `docker __complete compose -p … -f … <words…>`. This would fix the directory-scoped limitation above (explicit `-a` targeting, generated-override services) while keeping resolution inside the binary. Untested — Xcind proved the direct `docker __complete` call only.

3. **Service name completion from YAML**: Instead of delegating to docker for service names, parse the compose file directly. This would also give the hardcoded fallback path real service names.

4. **Flavor-aware completion**: Show available flavors when completing after `-f`/`--flavor` flag.

5. **Custom shortcuts**: Allow users to define additional shortcuts in Scind config:
   ```yaml
   # ~/.config/scind/config.yaml
   shortcuts:
     artisan: "exec php php artisan"
     composer: "exec php composer"
   ```

   Enabling: `scind-compose artisan migrate` → `docker compose ... exec php php artisan migrate`

### Alternative Approaches Considered

1. **Integrated `scind compose` subcommand**: Would require reimplementing all docker compose argument parsing and completion. Rejected due to complexity and maintenance burden.

2. **Alias-only approach** (`alias dc='docker compose -p ... -f ...'`): Doesn't support dynamic context detection. Rejected.

3. **Separate commands per docker compose subcommand** (`scind-exec`, `scind-logs`, etc.): Fragments the interface unnecessarily. Rejected.

4. **Sourced shell function + `compose-prefix` eval contract**: The original design, on the assumption that only a shell function could get delegated completion. Rejected once the Xcind proof-of-concept demonstrated delegated completion from a standalone binary (see [Why a binary and not a shell function](#why-a-binary-and-not-a-shell-function)). The function cost an `eval` on every invocation, an empty-output error-detection workaround, and a per-shell reimplementation of docker's completion-context rewriting.
